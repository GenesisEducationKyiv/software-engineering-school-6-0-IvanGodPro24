# ADR-004: Винесення домену сповіщень в окремий мікросервіс

**Статус:** Прийнято

**Дата:** 2026-06-04

**Автор:** Ivan Nepotachev

## Контекст

Початково застосунок був реалізований як монолітний Node.js/Express API з окремим background worker процесом для обробки email-сповіщень. Такий підхід працював, але домен сповіщень був тісно пов'язаний з основним застосунком: API містив код для Nodemailer, HTML-шаблонів, email-сервісів та worker-логіки.

Сам факт наявності email-коду в API не є достатньою причиною для створення мікросервісу. Важливішим фактором було те, що відправка email є асинхронним side effect: основний API має лише створити задачу на відправку, а не чекати SMTP-провайдера. Notification domain не потребує прямого доступу до PostgreSQL, може працювати через стабільний контракт задачі в BullMQ і має окремі failure modes: retry-логіку, SMTP-помилки, рендеринг шаблонів та потенційне незалежне масштабування worker-а.

## Розглянуті варіанти

1. **Винести Subscription Service**

   * **Плюси:** Це центральний бізнес-домен системи.
   * **Мінуси:** Потребує складнішого розділення бази даних, транзакцій, API-контрактів і синхронної комунікації між сервісами.

2. **Винести GitHub Scanner**

   * **Плюси:** Scanner вже працює як окрема фонова задача.
   * **Мінуси:** Scanner тісно пов'язаний з таблицями `Repository` та `Subscription`, тому потребував би прямого доступу до основної БД або додаткового API.

3. **Винести Notification Service**

   * **Плюси:** Домен сповіщень має чітку відповідальність: отримати задачу, згенерувати email і відправити його через SMTP. Він не потребує прямого доступу до PostgreSQL і добре підходить для асинхронної комунікації через Redis/BullMQ.
   * **Мінуси:** Потрібно підтримувати окремий package, Dockerfile та окремий build у CI.

## Прийняте рішення

Обрано винести **Notification Service** в окремий мікросервіс у директорії:

```txt
services/notification-service
```

Основний API більше не відправляє email напряму. Він лише створює задачі в Redis/BullMQ черзі. Notification Service споживає ці задачі, рендерить шаблони та відправляє email через Nodemailer/SMTP.

## Комунікація між сервісами

Комунікація реалізована асинхронно через Redis/BullMQ:

Для цього сценарію потрібна саме черга задач, а не синхронний HTTP-виклик чи Pub/Sub: email-задача не повинна блокувати API-запит, але також не має губитися, якщо Notification Service тимчасово недоступний. BullMQ підходить для цього, бо працює поверх уже наявного Redis і дає готові механізми retries, backoff, concurrency та bulk-додавання задач без введення окремої інфраструктури по типу RabbitMQ або Kafka. Детальніше вибір брокера описано в ADR-005.

```txt
Main API / Scanner
        ↓
Redis / BullMQ Queue
        ↓
Notification Service
        ↓
SMTP Provider
```

Контракт задачі визначає тип email:

* `confirm-subscription` — лист підтвердження підписки.
* `new-release` — лист про новий реліз.

## Наслідки

**Позитивні:**

* Основний API більше не залежить від SMTP, Nodemailer і HTML-шаблонів, тому зміни в email delivery не зачіпають HTTP API напряму.
* Відправка email винесена за асинхронну межу: API може швидко завершити запит після створення задачі, а retry та помилки SMTP обробляються окремо.
* Notification Service не має прямого доступу до PostgreSQL і взаємодіє з основним застосунком через явний контракт задач у BullMQ.
* Worker можна масштабувати незалежно від API, якщо зросте кількість задач.

**Негативні:**

* Збільшилась кількість частин системи, які потрібно підтримувати.
* Потрібно підтримувати versioning і build package `@github-notifier/notification-contracts`, який містить контракт email jobs між основним API та Notification Service.
* Для повноцінного локального запуску тепер потрібно запускати не лише API, PostgreSQL і Redis, а й Notification Service.
