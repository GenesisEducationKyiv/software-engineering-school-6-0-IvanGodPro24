# ADR-002: Вибір інструменту для фонових задач та черг

**Статус:** Прийнято

**Дата:** 2026-05-06

**Автор:** Ivan Nepotachev

## Контекст

Система повинна сканувати GitHub API на наявність нових релізів та розсилати email-сповіщення підписникам. Робити це синхронно в головному потоці неможливо, оскільки це призведе до блокування API, тайм-аутів при масовій розсилці та неможливості повторних спроб при падінні мережі.

## Розглянуті варіанти

1. **Redis + BullMQ**
   * **Плюси:** Висока швидкість, підтримка затримок, вбудовані механізми повторних спроб, ізоляція воркерів від API.
   * **Мінуси:** Потребує підняття окремого інфраструктурного компонента Redis-контейнера.
2. **In-memory черги (напр., масиви в Node.js / setTimeout)**
   * **Плюси:** Жодної додаткової інфраструктури, найшвидша імплементація.
   * **Мінуси:** Усі невідправлені листи зникають назавжди при перезавантаженні сервера, неможливо масштабувати бекенд на кілька інстансів.
3. **RabbitMQ**
   * **Плюси:** Гарантована доставка, складна маршрутизація повідомлень.
   * **Мінуси:** Занадто важкий для поточної архітектури.

## Прийняте рішення

Обрано **Redis** як брокер повідомлень та кеш.

## Наслідки

**Позитивні:**

* Головний API-сервер відповідає користувачу миттєво (< 200ms), делегуючи важку роботу воркеру.
* Якщо SMTP-сервер впаде, повідомлення залишаться в черзі Redis і будуть відправлені пізніше.
* Redis додатково використовується для rate-limiting та кешування відповідей GitHub API.

**Негативні:**

* Збільшення складності інфраструктури.
